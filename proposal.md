# Project Proposal

## Proposal Title:
Admin on-site webapp

## Abstract:
During Splash and other events, administrators need real-time visibility and practical control over class registration and attendance. Currently, there is no dedicated mobile-friendly interface for admins to manage onsite operations, and key registration controls are spread across separate pages, each requiring a full reload. This project proposes an admin on-site webapp that provides live monitoring of class enrollments and program check-ins (students and teachers), toggles to open or close registration for individual classes, and access to overenrollment settings where supported by existing systems. The interface is intended to stay reasonably up to date and be optimized for use on tablets and phones during the event.

The existing admin portal (`onsitecore`) is primarily a desktop-oriented Bootstrap navigation page, not designed for mobile use and not well suited to showing a unified live view of the program. This gap has been tracked in issue #2672 since February 2019 and remains open under the Stable Release 17 milestone.

## The Solution
The student and teacher onsite webapps (issue #2671, PR #2507) already established a useful pattern for this type of interface. This project delivers the equivalent for admins: a new `adminonsite` module following the same architectural pattern, with its own URL space, mobile-first templates, and reuse of the existing webapp shell. A focused snapshot helper consolidates dashboard data, and a polling endpoint with client-side diffing keeps the dashboard live without requiring schema changes or heavier infrastructure. The existing desktop portal remains substantially unchanged, aside from a single new entry point in `onsitecore/mainpage.html`.

## Detailed Description

### Part 1 — Solution Workflow

**Module Architecture**

The admin webapp is a new standalone `AdminOnsite` extending `ProgramModuleObj` with `module_type = 'onsite'`, served at `/onsite/<program_url>/adminonsite/`. Key points:

- The main URL is auto-generated by `get_full_path()` in `base.py`, following the same module resolution path as `onsitecore`, `onsitecheckinmodule`, and the existing student/teacher webapps.
- Access is gated by `@needs_admin`. The `onsite` module type is already recognized in `urls.py`, so no routing framework changes are needed.
- All secondary endpoints (polling, section detail, registration toggles, search, and settings writes) are registered as `@aux_call` methods, resolving as top-level module view names such as `/onsite/<program>/snapshot/` and `/onsite/<program>/toggleregistration/`, not nested under the main page path.
- The existing desktop portal and onsite admin pages remain intact. The only integration change is a single new button in `onsitecore/mainpage.html`.
- Navigation follows three tabs from a persistent top nav bar: **Dashboard**, **Search**, and **Settings**, matching the lightweight pattern used by the student and teacher webapps. Tapping a class row opens a drill-down detail page with the registration state toggle, cap information, and section roster.

A new module is used rather than modifying existing pages because the existing `onsitecore` portal is a desktop navigation hub for pre/post-event admin work; the new webapp targets rapid event-day decisions on a phone or tablet. The student and teacher webapps establish a strong precedent for this pattern: new module, own URL space, own templates, keeping desktop workflows untouched and limiting integration to a single new entry point.

**Snapshot Function**

The core data contribution is a single well-structured helper, `get_admin_onsite_snapshot(program)`, inside the new module handler or an adjacent helper in `handlers/`:

- Starts from one optimized `ClassSection` queryset using `select_related` on parent class, category, and program, plus `prefetch_related` for meeting times, teachers, and moderators.
- Reuses existing section-level data (enrollment counters, registration state, room information, capacity) instead of introducing a broader system-wide service layer in the MVP.
- Adds lightweight dashboard-specific annotations: moderator count and timeslot grouping metadata.
- Reuses teacher/moderator check-in semantics from `TeacherCheckinModule.getMissingTeachers()` for current-day staffing status.
- Kept focused on the admin dashboard only; a broader shared refactor is intentionally out of scope.

**Delta Polling**

To keep the dashboard live without WebSockets or heavy infrastructure:

- The snapshot endpoint at `/onsite/<program>/snapshot/` is polled every 30 seconds.
- Each response returns the current dashboard state. The client diffs against the previous state and re-renders only changed rows, with no full page reload, no server-side `last_modified` tracking, and no Django signal overhead.
- After an admin changes a class setting, the client re-fetches that class immediately rather than waiting for the next polling cycle.
- This approach aligns with the codebase precedent in `bigboardmodule.py`.

---

**How It All Comes Together**

The module, snapshot function, and polling endpoint form one connected system:

1. An admin opens the webapp; the browser fires a full snapshot request. The helper queries the database once, reuses existing counters and staffing logic, and returns all sections grouped by timeslot. The dashboard renders instantly.
2. Every 30 seconds the browser polls again. The client diffs the new response against the last and re-renders only changed rows, with no full page reload and less redundant DOM work.
3. Tapping a class row opens the drill-down page with section details, roster, registration controls, and current cap information. My proposal is that any quick event-day cap adjustment should live in this drill-down flow, while the exact editing semantics are finalized during community bonding.
4. Toggling a registration state writes to `ClassSection.registration_status`. Existing registration and class-change flows already respect this field, so the change becomes visible to students on their next page load.
5. If the network drops, the dashboard degrades through Stale then Disconnected states rather than showing a blank screen. Write controls lock automatically. On reconnect, a full snapshot re-fetch restores the Live state without manual intervention.

### Part 2 — Feature Description

**1. Live Class Registration Dashboard**

- All classes grouped by timeslot, not a flat list, using the existing admin/onsite timeslot grouping pattern.
- Current timeslot accordion expanded by default; past and future slots collapsed with a class count badge.
- Each class row shows: class name, room, teacher name (flagged red if unassigned), enrolled count, attendance-related status when available from existing onsite data, and a color-coded fill bar (green below 80%, amber 80–99%, red at capacity).
- Each row also shows moderator coverage. A class with neither teacher nor moderator is treated as a high-severity flag; a class with no teacher but a moderator present is still flagged, but less severely.
- Classes that need attention (no teacher, no moderator, or over 90% full) can float to the top of their timeslot group.
- Auto-refreshes every 30 seconds with a "Last refreshed X seconds ago" freshness indicator.

---

**2. Per-Class Registration Toggle (MVP: two states; Soft Closed as stretch goal)**

Core MVP states: **Open** (registration active normally) and **Closed** (registration fully disabled).

Additional behaviour:

- The transition to Closed requires a confirmation step, the friction model @willgearty explicitly requested to prevent accidental closures during a busy event.
- All state changes are saved via AJAX with no page reload.
- Writes land on `ClassSection.registration_status` (line 298 of `class_.py`), already respected by existing registration and class-change logic.

**Soft Closed (stretch goal):** A third state where the class appears full to students while holding spots for walk-in admissions. Introducing Soft Closed requires a compatibility pass across `class_.py` (line 93), `adminclass.py` (line 76), `management.py` (line 35), `classchange.py` (line 155), and `lottery.py` (line 122). This will be explored during community bonding and implemented as a stretch goal if scope permits.

---

**3. On-the-Fly Cap Editing**

- Tapping a class row opens the class drill-down page with full class metadata, roster, registration controls, and current cap information.
- My proposal is that cap changes should happen from this drill-down page, since that matches the event-day workflow better than sending admins to a separate management page.
- I expect the MVP to focus on quick event-day adjustments for the selected class flow, while avoiding a premature commitment on whether the underlying write should apply at class level or section level.
- The exact write path, data field, and final edit semantics should be confirmed with the mentor during community bonding so the implementation matches existing registration logic cleanly.
- If cap editing is included in the final scope, the UI should still warn admins before saving values that could create obvious conflicts, such as setting a cap below current enrollment.

---

**4. Global Search and Admin Peek Mode**

- Single search input accepting class name, student name, teacher name, or barcode scan.
- **Class result:** room, fill status, and registration state.
- **Student result:** schedule for the day, enrolled sections, and current attendance context; tap to open a student detail view with quick actions such as **Check In, Check Out, and Print Schedule.**
- **Teacher result:** assigned classes and check-in status; tap to open a teacher detail view with quick actions such as **Check In and Check Out.**
- The proposal is to reuse existing onsite search and schedule logic where possible, while wrapping it in a mobile-friendly admin interface that is faster to use during the event.


---

**5. Three-State Graceful Degradation**

| State | Condition | Behavior |
|---|---|---|
| **Live** | Polls succeeding | All controls active; freshness indicator shown in muted text |
| **Stale** | No successful poll for 30–120s | Last known data visible; all write controls locked; amber banner |
| **Disconnected** | Failure beyond 5 min or N consecutive failures | Everything disabled; red banner; Retry button shown |

- On reconnect from any state, a full snapshot re-fetch resets the client to Live automatically.
- @willgearty explicitly endorsed graceful degradation. Stale data shown clearly is always better than a blank screen during an event.

---

**6. Settings Tab**

- Exposes program-level configuration shared across all admin devices.
- The initial focus is live overenrollment control using the existing `StudentClassRegModuleInfo` settings, with the exact set finalized during community bonding.
- The MVP keeps this tab intentionally narrow; it can be extended later for future onsite services if needed.

## Codebase Understanding and Related Issues

Before writing this proposal I read the following files directly. Only existing files are listed here.

| File | Key insight and relevance |
|---|---|
| `modules/base.py` | `get_full_path()` auto-generates the main module URL. `@aux_call` and `@main_call` are the patterns for every endpoint. `@needs_admin` and `@needs_onsite` are the two relevant permission decorators; `@needs_admin` is used here since this is an admin-only tool. `urls.py` hardcodes the recognized top-level areas including `onsite`, which is why `module_type = 'onsite'` is the correct choice. |
| `models/class_.py` | `ClassSection.registration_status` (line 298) is an `IntegerField` with `OPEN`/`CLOSED` choices and helper methods at lines 1292–1293. `ClassSection.max_class_capacity` is the section-level cap override field. Effective cap is computed through the existing section capacity logic together with `StudentClassRegModuleInfo`. |
| `management.py` | `ClassManageForm.save_data()` (line 82) is class-wide, not section-wide. `SectionManageForm.save_data()` (line 150) is a useful reference point while evaluating the eventual cap editing flow and deciding whether the final onsite write should be class-level or section-level. |
| `handlers/onsiteclasslist.py` | Provides the strongest existing reuse surface: `catalog_status()`, student search, schedule JSON, schedule updates, and print-schedule JSON are already implemented here for onsite admin workflows. |
| `handlers/onsiteattendance.py` | Contains `OnSiteAttendance` and the ~105s TTL cache, but those cached methods are program-level attendance timelines rather than a drop-in per-section dashboard snapshot. |
| `handlers/studentonsite.py` and `teacheronsite.py` | Direct architectural templates: own handler, own mobile-first layout, lightweight top-nav, and `@aux_call` pages for secondary views. These views are role-gated around `request.user` and are not reused directly for admin detail views. |
| `handlers/teachercheckinmodule.py` | `getMissingTeachers()` is the most relevant existing implementation for current-day teacher and moderator staffing status, which the dashboard can reuse semantically. |
| `handlers/bigboardmodule.py` | Already uses a polling-oriented, lightweight admin view pattern. Its refresh cadence directly informed the dashboard polling design. |
| `handlers/adminclass.py` | `AdminClass.timeslot_counts()` is a useful reference for grouping classes by timeslot in an admin context. The `OPEN` registration filter is one of the Soft Closed compatibility surfaces if that stretch goal proceeds. |
| `modules/module_ext.py` and `forms/admincore.py` | The overenrollment and cap behaviour controls live on `StudentClassRegModuleInfo`, not on program-level Tags. The settings tab reuses those existing settings rather than introducing a parallel configuration system. |
